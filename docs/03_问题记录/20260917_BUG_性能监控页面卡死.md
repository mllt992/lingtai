## 1. 现象描述

- **现象**：打开性能监控页面后，Loft 窗口响应变慢甚至无响应，整机也出现明显卡顿。关闭该页后逐渐恢复。
- **截图/录屏**：无（代码静态定位已足够）
- **错误信息**：无前端报错；表现为高 CPU / 高进程创建率（每秒拉起 PowerShell）

---

## 2. 复现步骤

1. 启动 Loft（Windows）
2. 侧边栏进入「性能监控」
3. 观察 5–10 秒：任务管理器可见频繁出现 `powershell.exe`，整机与应用卡顿

**环境**：
- 客户端：Loft Windows 桌面版（Tauri 2）
- 后端 feature：**未启用** `gpu-nvml`（`Cargo.toml` default features 为空）
- 默认刷新间隔：`monitor.refreshMs = 1000`

---

## 3. 期望行为 vs 实际行为

| 维度 | 期望 | 实际 |
|---|---|---|
| 表现 | 监控页流畅刷新，整机不受明显影响 | 程序卡死感，整机变卡 |
| 采样开销 | 轻量 sysinfo 刷新 | 每秒 spawn PowerShell + WMI 查询 |
| 锁 | 短暂持有 sysinfo Mutex | 持锁期间执行外部进程，拖垮托盘线程 |

## 4. 影响范围

- **受影响功能**：性能监控页；间接影响托盘指标（共享 `AppState.sys` 锁）
- **受影响用户**：所有 Windows 且未启用 `gpu-nvml` 的用户（当前默认构建路径）
- **是否阻塞业务**：是（监控主路径不可用）
- **是否已影响生产**：是（打包 exe 默认走 PowerShell 兜底）
- **是否需要紧急修复**：是

- 出现频次：每次进入监控页

- 性能监控自首版方案即包含 GPU 采集；`gpu-nvml` 为可选 feature，线上默认走 WMI 兜底。
- 托盘 `spawn_metrics_loop` 每 2s 也锁同一 `sys` Mutex（`lib.rs`）。

## 7. 根因分析

### 7.1 排查过程

- 检查点 1：前端 `monitor.ts` 每 `refreshMs`（默认 1000ms）`invoke('get_system_snapshot')` → 无 in-flight 去重，后端慢时请求会堆叠
- 检查点 2：后端 `get_system_snapshot` 在 **持锁** 状态下调用 `collect_gpus()`
- 检查点 3：`collect_gpus()` 在 `not(feature = "gpu-nvml")` 且 Windows 时，**每次** `Command::new("powershell")` 执行 `Get-CimInstance Win32_VideoController`
- 检查点 4：CPU/内存使用 `CpuRefreshKind::everything()` / `MemoryRefreshKind::everything()`，频率等字段无必要每秒刷新
- 检查点 5：即使启用 NVML，当前实现也是每次 `Nvml::init()`，同样过重

### 7.2 根因结论

**每秒采样路径里同步 spawn PowerShell 查 WMI**，且整个过程持有 `AppState.sys` Mutex，导致进程风暴 + 锁阻塞，表现为程序卡死与整机变卡。

### 7.3 触发条件

- 数据：无特殊数据
- 角色：本地桌面用户
- 并发：监控轮询 1s + 托盘 metrics 2s 共用同一 Mutex
- 时机：进入 `/monitor` 页 `onMounted` 启动轮询后立即触发

### 7.4 为什么之前没发现

- 代码视角：GPU 采集藏在 `collect_gpus()`，调用方未感知其是「秒级外部进程」
- 测试视角：开发机若启用 NVML 或本机 PowerShell 极快，短时打开不易察觉；长时间驻留才明显
- 上线流程视角：无性能基线检查（监控页 CPU/进程创建率）

### 7.5 相似代码排查（grep 结果）

| 文件 | 结论 |
|---|---|
| `commands/monitor.rs` `collect_gpus` | **本 BUG**，每秒 PowerShell |
| `commands/icons.rs` `extract_icon` | 也用 PowerShell，但为按需一次性调用且前端有缓存，不在轮询路径，不修 |
| `lib.rs` tray metrics | 只 `refresh_cpu_usage` + `refresh_memory`，本身不重，但会被本 BUG 的长持锁拖慢 |

## 8. 修复方案（待开发者确认）

### 8.1 修复策略

- [x] 直接修复

### 8.2 具体改动（已实施）

**后端 `monitor.rs` / `Cargo.toml`：**

1. **彻底移除 PowerShell GPU 兜底**：改为 Win32 `EnumDisplayDevicesW` 原生枚举适配器名称，不 spawn 任何外部进程。
2. **GPU 结果缓存**：静态列表 TTL 60s；`gpu-nvml` 时缓存 `Nvml` 句柄，每次只查 utilization。
3. **不再持 `sys` 锁做 GPU**：`get_system_snapshot` 只在短临界区内做 CPU/内存采样，锁外处理 GPU。
4. **降低每秒 refresh 成本**：轮询路径 `refresh_cpu_usage` + `refresh_memory`；brand/频率每 30s 刷新一次并缓存。
5. **Cargo.toml**：Windows 依赖增加 `Win32_Graphics_Gdi`。

**前端 `monitor.ts`：**

6. **in-flight 去重**：`refreshOnce` 在上一次未返回时不发起新 invoke。

### 8.3 可能的副作用

- GPU 卡列表/名称最长延迟约 30s 才更新（热插拔极少见；可接受）
- 无 NVIDIA 驱动时仍可能显示「驱动/NVML 不可用」或静态名称（与现状一致，utilization 本就为 None）
- CPU 频率在轮询中不再每秒刷新（展示为启动后缓存值，可接受）

## 11. 修复结论

- **根因**：每秒采样路径同步 spawn PowerShell 查 WMI，并持 `sys` Mutex
- **修复方式**：原生 `EnumDisplayDevicesW` + GPU 静态缓存 + 锁外 GPU + 每秒轻量 CPU/Mem refresh + 前端防重入
- **影响范围**：性能监控后端采样 + 前端轮询；托盘 metrics 间接受益（不再被长持锁堵住）
- **是否同类排查**：是，见 §7.5（`icons.rs` 非轮询路径，不修）
- **是否需要数据修复**：否
